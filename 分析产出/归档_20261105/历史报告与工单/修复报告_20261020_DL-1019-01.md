## 一、根因（与工单判断不同）

工单推测「抓取任务在收盘前执行」。复核后否定：10-16 那批数据是 **10-17 10:27（盘后）** 写入的。真正链路是：

```
主源部分失败 → 降级到 TDX 批量报价（tdx_protocol_quote）
            → 报价路由在非交易时段返回重置后的空快照
            → 无任何校验 → 落库 → daily:core 标 failed 但 publication_status=published
```

按来源拆解 10-16 当日，坏数据全部集中在一个来源：

| 来源 | 标的数 | 平均成交额 | 成交额 < 自身 20 日中位数 10% |
|---|---|---|---|
| `exchange` | 2,316 | 31,621 万 | 0（0.0%） |
| `bse` | 350 | 3,935 万 | 0（0.0%） |
| `tdx_protocol_quote` | 2,900 | **67 万** | **2,878（99.2%）** |

`quote_bars()` 取的是实时行情字段（`open_raw/high_raw/low_raw/price_raw/vol`），本质不是历史日线源；`last_closed_session()` 只能判断"哪个会话已收盘"，区分不了"周五 15:30"和"周六 10:27"。这是结构性脆弱点，不是一次性事故。

## 二、代码变更（防增量复发）

### 2.1 入库闸门：`steps/bars.py`

新增 `_tip_turnover_plausible()`，接到两个整板快照入口（TDX 报价 tip、交易所 tip）：

- 取上一交易日的逐标的成交额作为基准，与本批数据比对；
- **本批 ≥40% 标的低于自身前期 10%，或本批中位比值 <0.10** → 整批判为截断快照，**不写库**，符号交回逐标的扫描（每只 1 次请求）；
- 可比样本不足 30 只时弃权，保持原行为；
- 另加：`trade_date` 与今日不同 **且** 今日非交易日（周末/节假日）时，报价路由直接跳过——报价快照此时不描述任何会话。

实测判别力（用 10-16 真实数据双向验证）：

| 批次 | 中位比值 | 低于 10% 占比 | 判定 |
|---|---|---|---|
| `exchange` | 0.910 | 0.0% | 放行 |
| `tdx_protocol_quote` | **0.001** | **99.3%** | **拒绝** |

阈值与实测量级相差两个数量级，不存在误伤空间。

### 2.2 质量检查：`quality/session_completeness.py`（新增）+ `quality/audit.py`（注册）

新检查 `daily_bars_session_truncated`：

- 口径：某日单只成交额 < 自身近 30 个交易日中位数 10% 的标的占比；
- 阈值：≥20% 判该日为截断快照（实测正常日全部 <1%，10-16 为 51.7%）；
- 输出带上 `collapsed_by_source`，直接指出是哪个来源坏了——修复从哪下手不用再猜。

实测：

| 会话 | 命中 |
|---|---|
| 2026-10-16（修复前） | **51.7%**，`{tdx_protocol_quote: 2878}` |
| 2026-10-16（修复后）/ 10-15 / 10-19 / 09-30 / 08-25 / 07-15 / 06-15 | 0 |

已确认该检查在审计主路径（`_collect_lake_findings`）中正常执行，不误报。

**为什么原有检查没拦住**：`daily_bar_finality_findings` 只抓"同日盘中写入"，10-16 是次日盘后写的；`daily_bars_amount_completeness` 只抓 null 金额；`daily_bars_turnover_defect_findings` 只抓 0 值和单位错。截断快照的每一行都是"格式正确的真价格 + 正的成交量/成交额"，只有跟自身历史比才看得出来。

## 五、需要你处理的两件事

### 5.1 日更调度在 10-19 没有触发

manifest 里 10-19 全天没有任何 `daily:*` 记录（10-17 周六是正常的 `skipped_non_trading_day`）。所以这次不是"数据被污染"，而是**日更根本没跑**，缺了一整天。请确认宿主的计划任务（`[job.daily] run_at = "17:30"`、`core at = "16:00"`）是否还在生效。

### 5.2 跑 compact 时会被环境的删除守卫误伤

在 agent 环境里执行 `cne`，`PYTHONPATH` 注入的 `sitecustomize.py` 会把 compact 的整目录替换判成"批量删除"并中断（`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]`，2,618 个文件 > 阈值 50）。绕过方式是给该命令关掉守卫：

```bash
CODEBUDDY_SAFE_DELETE_ENABLED=0 cne run daily --trade-date 2026-10-19
```

这是执行环境的问题，**你自己的调度器直接跑 `cne` 不受影响**，不需要改。
